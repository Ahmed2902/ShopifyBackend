# Enhanced conversion signals

## Evidence and scope

Shopify Orders remain commerce truth for revenue, currencies, refunds and purchases. Advertising metrics remain provider-attributed evidence. Pixel sessions and journeys are observed first-party behavior. Stride first-party attribution is descriptive evidence, **not causal or incremental truth**. A customer never has one permanent acquisition source.

This feature extends the App Store readiness branch from backend #150 and includes the managed Meta setup from #148, with fixes for stale manual credentials and exhausted reauthorization retries. It does not merge those PRs. Frontend depends on App Store pages #99 and includes the managed conversion UX from #98.

## Acquisition

Classification version 1 stores channel, extensible source/provider string, paid (nullable), evidence basis and version alongside original allowlisted evidence. Precedence: Meta click, TikTok click, Google click/braid, explicit Meta link IDs, UTMs, recognized external referrer, direct, unknown. Conflicting clicks are reported by the classifier; precedence is deterministic, not a claim that one caused an order.

Channels: paid social, paid search, organic search, organic social, email, affiliate, referral, direct, other and unknown. A gclid/gbraid/wbraid proves observed Google paid-click evidence, not Search; explicit search medium is needed for Paid Search. Recognized Google Search/Bing referrers are search; Gmail is email and Docs/Drive/account referrers are referrals. Unknown Google subdomains are not assumed to be Search. An unknown UTM source with organic medium remains OTHER/unpaid; its raw source is preserved. Instagram/Facebook/TikTok/YouTube/Pinterest referrers are social. Affiliate identification currently requires an affiliate UTM; arbitrary referrers are not guessed to be affiliates. Unknown UTM sources remain in the raw `utmSource` field and normalize to OTHER. No provider enum expansion is needed.

All five UTM fields, fbclid, gclid, gbraid, wbraid, ttclid and existing numeric Stride Meta campaign/ad-set/ad IDs are retained separately. URLs strip query, fragment, credentials and checkout/account token paths. Email-like, URL-like and control-containing attribution values are rejected. Merchants must still avoid PII in campaign labels; no algorithm can reliably distinguish a person's name from a campaign label. Meta URL decoration is reused. Google/TikTok campaign IDs are not guessed or decorated without a supported contract.

Existing 30-day first/last/assisted touch materialization is preserved. Normalized dimensions augment individual touches rather than flattening visitor history. `/conversion-delivery/acquisition` derives classification from raw touch evidence and reports the latest 10,000 touches in 30 days, with explicit truncation. Exact resolved Meta campaign/ad-set/ad evidence is grouped separately, capped at 100 groups per channel/source. This sample is not a complete cohort or unique-customer count.

## Deterministic identity

Existing store-scoped anonymous visitor IDs join multiple sessions. Existing exact checkout/order linkage joins a session to Shopify commerce. The worker first verifies the canonical Shopify checkout token against the consented Pixel checkout token (Shopify API 2026-07 or newer), then requests only approved fields. A public collector order ID alone cannot authorize another customer's matching data. A canonical Shopify Order query supplies its Shopify Customer GID; browser checkout email/phone/name are never used as commerce truth. `StorefrontCustomerLink` connects an exact order to a store-scoped pseudonymous customer key. Repeat canonical customer IDs produce the same key in the same store; unrelated stores and different customers produce different keys. Shared browser devices never merge two customers transitively. Anonymous-only sessions cannot be claimed as a known customer without an exact order link.

Each store has an encrypted random 256-bit HMAC key. Identity is HMAC-SHA256 over version, store ID and canonical customer GID. Meta/TikTok adapters SHA-256 the pseudonym for their hashed external ID fields; Google does not receive external_id. No raw internal database ID is sent as an external customer identifier. Encryption-key rewrapping preserves identity; rotating/deleting the HMAC secret breaks prior matching intentionally. Uninstall/reinstall deletes the old secret and customer links. No global cross-merchant identity exists. Customer links are privacy-sensitive pseudonyms, not anonymous data.

The authenticated `/conversion-delivery/orders/:orderId/journey` endpoint expands only exact same-customer order links within 30 days, preserving chronological touches, first/last/assists and paid/organic counts. It excludes unrelated anonymous sessions and reports bounded truncation. No customer key is exposed.

## Matching and provider adapters

Enhanced matching is disabled by default. Both `SHOPIFY_ENHANCED_MATCHING_APPROVED=true` and an enabled destination's `enhancedMatching` setting are required. The flag represents an operator assertion of actual approval and operational readiness, not a permission grant from Stride. Request Shopify level 1 data access and individual level 2 name/address/email/phone fields, document advertising use, and obtain the required review before enabling it. `SHOPIFY_ENHANCED_MATCHING_FIELDS` enumerates the fields actually approved for this app: email, phone, name, address, customer_id and separately opt-in client_ip. Remove unapproved fields from that operator allowlist; no arbitrary GraphQL fields can be added. `read_orders`, API version and a current installation are checked before protected access. Missing/mismatched checkout proof or an old API version preserves permitted browser/click delivery and reports a reason. Missing/unapproved data is omitted; no empty hashes or fabricated defaults.

Raw customer fields and canonical client IP exist only in worker memory during a verified canonical Shopify query and provider send. Provider-neutral enrichment is cached only for the bounded worker batch; each provider still performs its own final consent/billing/destination check. They are not persisted in the inbox, delivery queue, coverage APIs or logs. Matching hashes also remain in memory. Email casing and surrounding whitespace normalize; Meta phones hash country-code digits without `+`; TikTok and Google phones hash explicit E.164 including `+`. National phone countries are never inferred. Unicode names remain Unicode; punctuation is removed before hashing. Google Gmail/googlemail local parts remove dots and plus suffixes, and intermediate whitespace is removed. Google supports at most ten one-of identifiers, and addresses require both names, ISO country and postal code. Google country/postal remain un-hashed. Meta location fields hash separately. TikTok uses its own user schema, not Meta's.

| --------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Meta CAPI             | existing _fbc or actual click-derived fbc, existing _fbp, hashed external_id/email/phone/name/location; observed UA and approved canonical Purchase IP  | PageView, ViewContent, AddToCart, InitiateCheckout, Purchase |
| TikTok Events API 2.0 | ttclid, existing _ttp as ttp, hashed external_id/email/phone; observed UA and approved canonical Purchase IP                           | ViewContent, AddToCart, InitiateCheckout, Purchase           |

Browser cookies are read through Shopify's asynchronous browser API only with analytics, marketing and sale-of-data permission. `_fbc`/`_fbp`/`_ttp` are never fabricated. The opt-in Meta storefront app embed can use a genuine official browser SDK cookie; see CONVERSION_SIGNAL_VALIDATION.md. An existing _fbc supplies its original creation timestamp when it matches the observed fbclid; without it, fbc is derived only from an actual observed click and its observation time. A conflicting cookie never replaces a newly observed click. UA comes from Shopify event context, not HTTP collector headers. IP is never taken from collector/proxy headers or a browser-supplied field. For verified canonical Purchases only, Shopify Order.clientIp can supply it to Meta/TikTok when client_ip is explicitly approved and allowlisted; it is not persisted. Funnel IP remains unavailable, and Google receives no IP through the existing Data Manager contract. No canvas/GPU/audio/font/screen fingerprinting occurs. Meta browser cookies often do not exist when no browser Meta integration created them; absence is reported, not replaced.

Funnel sharing is separately opt-in for Meta/TikTok. Google is not a generic analytics ingestion sink. TikTok's current standard event list omits PageView, so Stride does not invent one. Product/cart/checkout observations are Pixel truth; Purchase time/value/currency/order are canonical Shopify truth. Unknown funnel money is omitted. Funnel events are selected in background within 48 hours; collection adds no provider HTTP calls or Shopify customer queries. Bounded keyset sweeps advance over ineligible tenants and wrap to reconsider recovered entitlements. The cursor is a per-worker scheduling hint; restart replay remains safe through durable event uniqueness.

The product-content and controlled storefront browser path extension is documented in [CONVERSION_SIGNAL_VALIDATION.md](CONVERSION_SIGNAL_VALIDATION.md), including exact catalog mapping, batched diagnostics, overlap policies, SDK consent and live-provider deployment gates.

## Consent, lifecycle and deduplication

Collection requires analytics permission. Advertising use additionally requires marketing and sale-of-data permission. Worker eligibility and actual HTTP send independently recheck durable consent, active installation generation, source event, exact order existence, current destination settings/ownership, provider connection permissions and current billing entitlement. Cross-session click evidence is reselected under its own withdrawal markers at send time. Disabling enhanced matching after preparation blocks its stale prepared payload. OAuth refresh does not bypass the final check.

Withdrawal stores only minimal scope IDs in a browser privacy-operation queue until collector acknowledgement, including across reloads. Retries keep every unacknowledged scope and serialize storage writes. Advertising permission is sticky-false for an already queued/in-flight batch, even on a later regrant. Landing evidence and browser matching are cleared from that batch. Server withdrawal tombstones prevent replay of older events from being reauthorized. New consent can authorize new observations; it does not authorize old stored events or queued identifiers. Customer links related to withdrawn sessions are deleted. Uninstall and generation invalidation clear browser evidence, identity keys/links and queued sends. Existing customers/redact, shop/redact and order-redaction protections remain, including funnel rows related to redacted sessions.

No system can retract an HTTP request already sent before a withdrawal reaches it; the final check runs immediately before provider HTTP dispatch. Storefronts closed before persisting a privacy operation, unavailable browser storage, and unavailable networks remain explicit environmental limits. A persisted operation resumes on the next Pixel load. Duplicate privacy operations are safe.

New event IDs hash store ID plus stable source event ID (Purchase uses canonical Shopify order ID), yielding `stride:event:<sha256>`. Database uniqueness covers destination/event ID and destination/order/event type; legacy Purchase records cannot be re-enqueued under a new ID. Retries and crash recovery reuse the ID; distinct actions/stores differ. The opt-in Meta theme embed now controls a paired storefront PageView/ViewContent/AddToCart path; checkout and Purchase remain server-side. No deduplication against Shopify native integrations or unrelated tracking apps is claimed. The controlled adapter uses exactly this same ID and matching provider event name; identical ID alone does not prove an unrelated integration deduplicates.

## Retention and diagnostics

Raw customer fields, canonical client IP and provider customer hashes: worker memory only. Encrypted browser ID/UA bundle: at most 48 hours, with bounded cleanup and immediate clearing on withdrawal/uninstall. Raw Pixel events and existing journeys retain their configured, bounded retention and 30-day journey semantics. Customer links expire after 90 days. Click IDs/source URLs clear on successful delivery or permanent failure; pending/retrying events expire after seven days. Existing consent tombstones outlive the delivery/replay window. Store HMAC keys last for the installation and are removed on uninstall/shop purge. Existing anonymized aggregate analytics are separate from personal identifiers.

`/conversion-delivery/signal-health` reports per-provider destination status, OAuth connection status/permissions/expiry where observable, bounded delivery counts and last success, reason codes, commerce purchase count and identifier coverage. It exposes no secrets, customer values or matching hashes. Coverage denominator is the number of queue rows where evidence was prepared, not all Shopify orders, unique people, successful matches or a causal score. Rows may span multiple destinations. `DELIVERED` means the API accepted/acknowledged the request; Google requestId does not establish downstream matching. No invented Meta Event Match Quality or opaque Stride score is supplied. Absent API integration does not claim that Meta could never expose quality data.

## Rollout and limitations

Apply migration 52 after the #150 chain; it adds nullable fields, two identity tables and tenant constraints without dropping rows. Validate against a production-sized shadow database before deployment: strengthened foreign keys and unique indexes intentionally reject existing invalid/duplicate rows rather than silently deleting them. Deploy backend before companion UI. Keep enhanced matching off until Shopify approval, merchant disclosures, encrypted backups, staff access controls/logging, incident response and environment separation are verified. Those operational approvals are not fulfilled by an environment variable.

Live provider testing must cover test-event codes, managed Meta dataset ownership, TikTok pixel token ownership, Google conversion-action type and online/enhanced-conversion eligibility, Data Manager scope/access, hashed normalization, consent, deduplication, expiry, withdrawal races and provider diagnostics. No live provider traffic was authorized/configured in this implementation session. TikTok and Google destination auto-discovery remains unavailable in the existing managed setup API; pre-existing configured destinations can use enriched signals. This does not promise universal matching, cookie creation, recovery of denied/blocked visitors, native integration deduplication, every provider's proprietary score, or WeTracked-like causal/revenue claims.

## Deployment validation

The migration runs atomically. If legacy rows violate the strengthened constraints, the previous schema remains intact. Before deployment, inspect duplicate Purchase keys and mismatched destinations in a read-only production snapshot; investigate them rather than deleting customer or commerce records automatically.

```sql
SELECT "destinationId", "sourceOrderId", "eventName", COUNT(*)
FROM "ConversionDelivery"
GROUP BY "destinationId", "sourceOrderId", "eventName"
HAVING COUNT(*) > 1 LIMIT 50;

SELECT d."id"
FROM "ConversionDelivery" d JOIN "ConversionDestination" dest ON dest."id" = d."destinationId"
WHERE d."storeId" <> dest."storeId" OR d."provider" <> dest."provider"
LIMIT 50;
```

Measure index/constraint creation locks on a production-sized shadow before scheduling deployment. Report reads use bounded windows and tenant/session indexes; the acquisition sample is capped at 10,000 results, while queue health counts all rows in the 30-day tenant window. Extremely high-volume stores still need capacity/load verification for those window counts. Collector transactions take shared installation locks so parallel batches remain concurrent while privacy and lifecycle writes serialize; no Shopify/provider HTTP calls occur in collection. Enrichment performs two canonical queries per unique verified Purchase per bounded worker batch, rather than independently for every provider.
